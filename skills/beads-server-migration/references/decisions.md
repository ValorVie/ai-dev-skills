# 切換前的限制與取捨

伺服器模式讓同一個 repo 的 `bd` 程序共用本機 Dolt 服務，適合有並行鎖等待或逾時的環境。每個 repo 使用自己的服務、資料目錄與通訊埠。先量測目前延遲與服務資源用量，再判斷是否值得切換。

一次八個程序並行的副本測試中，伺服器模式平均延遲約快 7～8 倍；另一次現場唯讀命令從 7～23 秒降到約 0.2～0.3 秒。這些是特定工作負載的結果，不是其他環境的保證。該次服務啟動一分鐘後約使用 200 MiB 記憶體。服務停止時，依賴它的 `bd` 命令無法連線；還需預留磁碟、獨立通訊埠及 Dolt 版本維護成本。

## 切換時要守住什麼

- 經過測試的 `bd` 1.3.1 在 `bd init` 時會把既有 `.beads` 改為 `0700`。在目標目錄外的暫存 repo 初始化，保留目標原有的 owner、group、mode 與 ACL（存取權限清單）；先確認其他版本的行為。
- 切換前停止所有 `bd`，包括排程、Git hooks 與其他 worktree 呼叫的程序，並維持停用直到驗收或退回結束。工作區 gate 鎖檔依 inode（檔案身分）加鎖，不可刪除或改名，否則同名檔可能代表不同的鎖。
- 選庫環境變數可能讓 `bd` 連到另一份資料。套用前拒絕任何已設定的選庫變數，子程序也必須清除這些變數；不要把指向目標 repo 的目前目錄當成充分證明。
- 檢查程序及資料樹是否仍在使用。一般程序即使和操作者同帳號，也可能因不可傾印而無法讀取 `/proc` 的檔案描述符；其他帳號的程序也可能不可讀。程序名稱與可見性檢查有其限制：若其他帳號用改名的執行檔存取資料，單靠名稱無法發現。操作前須確定所有相關程序的身分與入口可控；無法確認便停止。容器只能顯示自己的程序命名空間，容器演練不能證明主機的 `/proc` 可見性。
- 混合擁有者的 `metadata.json` 使用原 inode 寫入，避免替換檔案時改變 owner 或 ACL。這不是原子寫入；先保存原內容與檢查點，中斷時依退回程序核對並續跑。
- Dolt 原生 backup／restore 不帶 remotes（遠端設定）。還原後重新核對遠端，經授權再設定；不要把備份完成視為同步完成。
- 切換後將已核對的 `metadata.json` 納入 Git 提交。核對每個 worktree 的選庫結果與實際 Git hook 連線；只看到 commit 成功，不代表 hook 已連到正確資料庫。
- 查核 `dolt.auto-commit` 的實際設定。若為 off，經授權先執行 `bd dolt commit` 再同步；push 成功不保證未提交的資料已送出。`bd dolt push` 若完整性檢查逾時，先調查資料量與原因，必要時設定 `BEADS_FSCK_TIMEOUT` 後重試，不要跳過檢查。

## macOS

macOS 未驗證。若未來移植，需要另外設計 `launchd` 服務、程序和開檔檢查，以及等效的鎖、權限與回復測試；Linux 腳本和 Docker 結果不能直接當成 macOS 的驗收證據。
